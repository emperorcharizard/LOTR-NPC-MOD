# How this project works across threads

This project is built to survive moving to a new thread. Nothing important lives only in a conversation: the state, the decisions and the source all sit in the project, so a fresh thread rebuilds everything from there. Move to a new thread whenever the current one gets long, starts summarizing ("compacting") earlier messages, or hits an attachment limit.

**Rebased 2026-11-07 at 0.0.97** (second account; the owner's four Haradrim .bbmodels were too big for the patch): this bundle, `lotrnpcs-handoff.zip`, is the new **base**; there are no patch parts until the next change. If the project's `lotrnpcs-handoff.zip` is older (its HANDOFF.md doesn't say "rebased at 0.0.97"), stop and ask the owner to upload the 0.0.97 bundle. The project's `claude/HANDOFF.md` may lag behind: the one inside the bundle (plus any patch parts) is current.

## What holds what

| Where | What | Changes |
| --- | --- | --- |
| `lotrnpcs-handoff.zip` (project file) | **The base:** full source, tools, tests, build inputs, docs and memory, as of 0.0.97. Source hash `f2e42b1c3589cb26` (below). | Only when rebased |
| `source/source-1.patch`, `source/source-2.patch`, ... (project docs, since 0.0.93) | **Every change since the base,** one unified diff split at file boundaries into parts of at most about 40 KB (`patch -p1` inside `lotrnpcs-handoff/`, the parts in number order). Text only. The parts carry the current `HANDOFF.md`, `THREADS.md`, docs and source. | End of every round |
| `HANDOFF.md` (project doc `claude/HANDOFF.md`) | The briefing: decisions, rules, layout, build steps, open questions, current state. **Since 0.0.93 the current copy is the workspace's `HANDOFF.md` after the patch parts are applied;** the project doc can lag behind, because a file over about 25k tokens can't be uploaded from the workspace in one piece (HANDOFF is about 42k). | End of every round (workspace copy) |
| `THREADS.md` (project doc, this file) | The thread procedure and the round log below. | End of every round |
| The user's computer | Test zips, game logs, screenshots, modpack zips, the weapon models in progress. | Uploaded when needed |

**Source hash:** sha256 of all `.cs` and `.py` files under `lotrnpcs/src`, `lotrnpcs/tools/gen_testnpcs.py`, `lotrnpcs/tools/bundle_lrc.py` and `lotrnpcs/tools/tests`, sorted by path and concatenated, first 16 hex digits.

## Starting a thread (do this first, silently, then report in two or three lines)

1. Read `THREADS.md` (this).
2. Rebuild the workspace: unzip the project file `lotrnpcs-handoff.zip` into a new folder; read every `source/source-N.patch` that exists (large docs come back as a local file; an old single `source/source.patch` counts as part 1) and apply them in number order with `patch -p1` inside `lotrnpcs-handoff/`. Check the source hash against the round log's latest. If it differs, say so before doing anything.
3. Read the workspace's `lotrnpcs-handoff/HANDOFF.md` in full (in pieces with offset and limit; it's large). The "Summary" in section 3 and the round log are the latest truth; older numbers in `docs/design-doc.md` lose to them.
4. Set up .NET 10 (HANDOFF section 7; if apt can't reach the Ubuntu archive, switch apt to https through the proxy as written there). If it can't be installed, say so plainly and ask the user to turn on network access for code execution; Python asset generation still works.
5. Tell the user which round you're on, what's built versus only written, and the one most important open question. Then follow the working rules in HANDOFF section 2.

## Ending a round (every time something is built, decided or changes)

1. Update the workspace `HANDOFF.md`: section 3 Summary, the untested list, open questions. (Upload it to `claude/HANDOFF.md` too if the upload tool accepts it; the patch carries it either way.)
2. Regenerate the patch with `a/` and `b/` paths (HANDOFF section 7): `ln -s <fresh base>/lotrnpcs-handoff a; ln -s <workspace>/lotrnpcs-handoff b; diff -ruN --exclude=dist --exclude='*.png' --exclude='*.pdf' --exclude=__pycache__ --exclude=bin --exclude=obj --exclude=out a/ b/`. Split it at `diff -ruN` lines into parts of at most about 40 KB, check the parts reproduce the tree on a fresh base, read each part in full and write them to `source/source-1.patch`, `source/source-2.patch`, ...; delete any higher-numbered part left from an earlier round.
3. Add a line to the round log below, with the new source hash.
4. Send the user the test zip and any new preview images (the project can't store binaries).
5. Write project docs only at the end of a round, not mid-work.

## Moving to a new thread

- **When:** the thread starts summarizing earlier messages, gets slow, nears an attachment limit, or the user asks. Suggest it at the end of a round, never mid-task.
- **Before moving:** run "Ending a round" so the docs are current.
- **The user then** opens a new chat in this project and sends: *"Continue the LOTR NPC mod. Follow THREADS.md to start the thread."*

## Rebasing (when the patch gets big, or moving accounts)

If the patch parts together grow past about 300 KB, or the user moves to another account: build a fresh `lotrnpcs-handoff.zip` from the workspace (source with `dist/` holding only the latest zip, `docs/`, `memory/`, `build-inputs/`, `HANDOFF.md`, `CARRY-OVER-CHECKLIST.md`, `THREADS.md`), send it to the user, have them replace the project file, and start the patch over. Update the source hash above.
